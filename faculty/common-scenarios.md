# IT 140 Faculty | Common Scenarios

Use these examples as quick routing guidance. Follow the linked page when the situation needs more detail.

## A Student's Local Setup Is Failing

**Faculty response:**

* Keep coursework moving in the CVD.
* Do not improvise operating-system repairs.
* Preserve the error/Verify result.
* Refer the technical problem to the IT Service Desk.

See [Supporting Students](supporting-students.md#for-technical-environment-problems).

## A Student Uses a Chromebook or Tablet

Use the CVD.

Students do not need a supported local installation to complete IT 140.

See [Unsupported or Best-Effort Environments](../shared/supported-environments.md#unsupported-or-best-effort-environments).

## A Student Asks, "What Do I Submit?"

Use the current **D2L Brightspace Guidelines and Rubric**.

Do not infer required deliverables solely from the files present in the GitHub repository.

See [Assignments and Grading](assignments-and-grading.md).

## A Student Says "GitHub Isn't Working"

Identify what that means before routing:

* cannot sign in/authenticate → technical support;
* cannot create/clone the repository → technical support;
* opened the wrong repository copy → orient using the Three-Copy Model;
* does not understand Git/GitHub concepts → faculty/LSS may provide learning support;
* public course repository is missing/broken → course technical escalation.

See [GitHub and Student Repositories](github-and-repositories.md).

## A Student Changed Computers or Reset the CVD and Cannot Find the Assignment

Do **not** create a new repository immediately.

If the student's private GitHub repository contains the work, clone that existing repository into the new environment.

See [Moving to Another Computer or a Reset CVD](../shared/github-workflow.md#moving-to-another-computer-or-a-reset-cvd).

## A Student Is Repeating IT 140

The student should use repositories created from the **current course templates** for the new attempt.

Do not direct the student to continue using an old assignment/project repository as the active current-course repository.

See [Repeat Students](../shared/github-workflow.md#repeat-students).

## A Student's Python Program Runs but Produces the Wrong Output

This is usually a student-code/learning problem rather than an environment failure.

Faculty may:

* help identify the unexpected result;
* ask the student to trace the logic;
* connect the issue to current course concepts; and
* refer the student to an appropriate [Academic Support](../academic-support/README.md) learning option.

For IT 140-focused live support, LSS is appropriate. For on-demand general Python support, 24/7 Drop-In Tutoring may be appropriate.

Do not send a normal student logic error to the Service Desk merely because the program was run in VS Code.

## A Student Is Falling Behind Because They Cannot Organize the Week

This is not automatically an instructional or technical failure.

A useful general pattern is:

* begin early in the week;
* plan approximately **2–2.5 hours per day**;
* prioritize current zyBooks Participation/Lab Activities;
* then complete the current module assignment/milestone; and
* use remaining planned time for the active Text-Adventure Game project.

Current Brightspace due dates take precedence.

**Route:** [Academic Coaching](../academic-support/coaching.md#time-and-task-prioritization) when the student needs help creating or following the plan.

## A Student Has Trouble Following Technical Directions

If the issue is reading, sequencing, or organizing the directions, [Academic Coaching](../academic-support/coaching.md#reading-comprehension-and-technical-documentation) may be appropriate.

If the student follows the current documented step and the technology fails, route to the IT Service Desk.

## A Student Wants You to Look at Their Private GitHub Repository

Do not ask the student to make it public.

If direct review is appropriate, the student may grant faculty collaborator access through the approved GitHub workflow.

See [Reviewing a Private Student Repository](github-and-repositories.md#reviewing-a-private-student-repository).

## A Repository Test Fails

First determine **what failed**:

* student code fails a valid course test → student learning/assignment issue;
* test itself appears incorrect or inconsistent with the current rubric → possible course technical defect;
* Python/test tooling cannot run → technical environment issue.

Do not automatically treat a local test failure as a grading result unless the current Brightspace activity says to do so.

## Brightspace and the Repository Seem to Say Different Things

Use Brightspace for the graded requirement.

Capture the conflicting language and report the documentation conflict.

See [If Brightspace and GitHub Appear to Conflict](assignments-and-grading.md#if-brightspace-and-github-appear-to-conflict).

## You Have Not Taught IT 140 Recently

Do not begin from your previous local repositories or remembered commands.

Use the [Start-of-Term Reorientation](start-of-term.md), the live Course Status page, and the current activity README.

## Several Students Report the Same Technical Failure

This may indicate a course-provided or platform-wide defect.

* Check Course Status.
* Preserve one or more clean reproduction examples.
* Avoid collecting unnecessary student-specific data.
* Reproduce in the CVD when reasonable.
* Escalate through the course technical path.

See [Technical Issues and Escalation](technical-issues-and-escalation.md#course-provided-content-appears-defective).
