# IT 140 Academic Support | Academic Coaching

This guide is for **Academic Coaches and other SNHU F&S personnel** who want enough IT 140 context to help a student build effective academic habits without needing to teach Python or troubleshoot the course technology.

Academic Coaching is goals-based support. In IT 140, coaching can be particularly valuable because students must learn new programming concepts while also managing a fast-paced eight-week workflow, reading detailed technical directions, organizing work across several systems, and solving problems incrementally.

> [!IMPORTANT]
> Coaching should focus on **how the student plans, reads, organizes, learns, and solves problems**. Programming instruction belongs to faculty/LSS/tutoring; technical failures belong to the IT Service Desk; graded-requirement interpretation belongs to faculty.

## IT 140 Context for Coaches

* **Course:** IT 140 - Introduction to Scripting.
* **Length:** Eight weeks.
* **Programming language:** Python.
* **Prior experience:** Previous programming experience is not required.
* **Workload context:** A three-credit course in this format should require about **16 hours per week on average for an average student**.
* **Pace:** Concepts build from week to week. Falling behind early can make later work harder.
* **zyBooks:** A significant source of instruction and hands-on practice, especially early in the course.
* **Development work:** Students complete smaller assignments and then design, prototype, and build a text-based adventure game across Modules Five–Seven.
* **Development process:** IT 140 emphasizes breaking problems down, designing before coding where appropriate, developing incrementally, testing, and debugging.
* **Reference environment:** The Codio Virtual Desktop (CVD); supported local setup is optional.
* **Graded requirements:** Current D2L Brightspace Guidelines and Rubric are authoritative.

## Coaching Areas That Map Well to IT 140

| Coaching Area | Useful IT 140 Focus |
| --- | --- |
| Time and Task Prioritization | Start early, work in daily blocks, complete current learning/practice before rushing ahead, leave time for debugging and help |
| Reading Comprehension | Read, understand, and follow technical documentation and multi-step instructions |
| Strengthen Academic Skills | Build consistent practice, self-checking, note-taking, help-seeking, and reflective learning habits |
| Support for Learning Differences | Use task chunking, predictable routines, reduced context switching, externalized checklists/logic, and other individualized learning strategies |
| Critical Thinking and Problem Solving | Decompose problems and follow the course SDLC instead of jumping directly to a finished solution |
| Organization | Track work across Brightspace, zyBooks, GitHub, repositories, the IDE, due dates, and the multi-module project |

## Time and Task Prioritization

### A Practical Weekly Pattern

A useful default coaching recommendation is:

> **Start early in the week and plan approximately 2–2.5 hours of IT 140 work each day.**

That pattern distributes roughly the expected weekly course effort while leaving room to adjust for the student's other courses, work/life obligations, specific module load, and actual due dates.

The purpose is not to require an identical daily schedule. The purpose is to avoid concentrating an entire programming week into the weekend, when there may be little time left to:

* discover that a concept is harder than expected;
* debug a program;
* ask the instructor a question;
* use tutoring or a live support session; or
* recover from a technical failure.

### Default Priority Order

When a student needs help deciding what to do next, a useful default priority is:

1. **Current zyBooks Participation Activities and Lab Activities**
2. **Current module assignment or milestone**
3. **If planned time remains, continue the active Text-Adventure Game project**

This order reinforces learning before later development work. Current Brightspace requirements and due dates always take precedence over this general planning rule.

For Modules Five–Seven, the project intentionally spans multiple weeks. A student should make steady progress on it without skipping current learning activities or the current module's required work.

### When the Student Is Already Behind

Help the student reduce the situation to a manageable next action.

Useful coaching questions include:

* Which **current required item** is incomplete?
* Is the student behind primarily in **zyBooks, the module assignment/milestone, or the project**?
* What can reasonably be completed in the **next 30–60 minutes**?
* Is the blocker **time/organization, understanding programming, assignment interpretation, or technology**?
* Which support path can address that blocker **today**?
* What is the next planned work block after this one?

Avoid building an elaborate recovery schedule before identifying the first actionable task and the type of barrier.

## Reading Comprehension and Technical Documentation

IT 140 asks students to read and follow technical documentation much more precisely than many nontechnical courses.

Examples include:

* exact filenames and folder paths;
* ordered setup or repository steps;
* command-line instructions;
* starter-file directions;
* expected program behavior;
* pseudocode/flowchart requirements;
* test instructions; and
* submission requirements.

A student may understand the general idea yet still struggle because technical documentation often depends on **small exact details**.

### Source Hierarchy Coaches Should Know

| Question | Correct Source |
| --- | --- |
| What does the graded activity require? | Current D2L Brightspace Guidelines and Rubric; faculty interprets |
| How does the student use the activity repository? | Current public activity repository `README.md` |
| What programming concept is being learned? | Current Brightspace module and zyBooks |
| How is the course IDE set up? | Current Module One Setup Tasks |
| A course tool or repository command fails technically | IT Service Desk |
| What does an IT 140 term mean? | [Course Glossary](../shared/glossary.md) |

### A Technical-Reading Routine

A coach can help the student practice this sequence:

1. **Identify the goal.** What will be true when this step is complete?
2. **Read the entire current step before acting.**
3. **Mark exact names.** Filenames, folder names, command text, required output, and submission format matter.
4. **Separate requirements from examples, tips, and optional practice.**
5. **Do one step at a time.**
6. **Compare expected and actual results before continuing.**
7. **Stop at the first unexpected result** instead of stacking more changes on top of an unknown problem.
8. **Use the correct support path** when rereading does not resolve the issue.

This is an academic reading strategy, not technical troubleshooting.

## Strengthen Academic Skills

Useful general academic habits for IT 140 include:

* **consistent practice:** frequent shorter programming sessions usually support learning better than one compressed session;
* **active notes:** record what a concept does, a small example, and a common error instead of copying long passages;
* **self-checking:** predict an output before running code, then compare prediction with actual behavior;
* **incremental progress:** finish and verify one small piece before adding the next;
* **early help-seeking:** ask for support while there is still time to apply it;
* **reflection:** after fixing an error, identify what caused it and what clue revealed it; and
* **productive persistence:** try a small number of purposeful steps, then seek help rather than repeating the same unsuccessful action for hours.

Coaches do not need to judge the correctness of the programming solution to reinforce these habits.

## Support for Learning Differences

Students with diagnosed learning differences may benefit from individualized academic strategies. Coaches can apply normal Academic Coaching practices while using IT 140's structure to make those strategies concrete.

Potential strategies include:

* break a long README or assignment into small checkpoints;
* convert multi-step directions into a personal checklist;
* use a predictable daily study routine;
* reduce unnecessary switching among Brightspace, zyBooks, GitHub, and VS Code;
* keep the current instruction page visible while doing the corresponding task;
* annotate technical directions with brief plain-language notes;
* use timers and planned breaks when sustained technical attention is difficult;
* externalize program logic with pseudocode, a flowchart, or a small hand-traced example;
* maintain a brief "next action" note at the end of each work session; and
* separate **learning the concept** from **operating the tool** so the student knows what kind of help to seek.

These are learning and organization strategies. They do **not** replace formal accommodation processes or authorize changes to course requirements. Questions about accommodations or graded requirements should follow the appropriate university/faculty process.

## Critical Thinking and Problem Solving

Critical thinking and problem solving are core programming skills in IT 140.

The course repeatedly asks students to move from a problem to a deliberate solution rather than immediately typing a finished program. Coaches can reinforce that process without writing code.

### A Simplified IT 140 SDLC

| Phase | Student Thinking |
| --- | --- |
| **Analysis** | What is the problem? What are the requirements, inputs, outputs, rules, and constraints? |
| **Design** | What steps should happen? Would pseudocode, a flowchart, storyboard, or map make the logic clearer? |
| **Development** | What is the smallest useful piece that can be implemented now? |
| **Testing and Debugging** | What did I expect? What actually happened? Which small test can isolate the difference? |

This pattern appears across IT 140:

* early activities introduce small programs;
* Module Three uses flowchart/pseudocode design;
* Module Four designs a looping higher/lower game;
* Project One designs the text-based game before full implementation;
* Module Six develops a simplified prototype; and
* Project Two integrates the full game incrementally.

### Coaching Prompts

Useful process questions include:

* What do you already know from the requirements?
* What is the **next decision** the program must make?
* Can you describe the logic in plain language before thinking about Python syntax?
* What is one small example you can work through by hand?
* What is one small test that would tell you whether this part works?
* What changed between the expected result and actual result?
* Is the remaining barrier a **programming-learning question**, an **assignment question**, or a **technical failure**?

If the student needs help deciding *how Python should express the logic*, route to faculty, LSS, or tutoring. The coach's value is helping the student establish a repeatable problem-solving process.

## Organization

IT 140 work is distributed across several systems. A student can feel disorganized even when each individual tool is functioning correctly.

### Systems Map

| System | Primary Purpose |
| --- | --- |
| **D2L Brightspace** | Weekly course content, graded requirements, due dates, submissions, grades, instructor feedback |
| **zyBooks** | Interactive programming instruction, participation activities, labs, and practice |
| **Public GC-STEM GitHub repository** | Course-provided activity instructions, templates, starter resources |
| **Student's private GitHub repository** | Student development work and Git backup/history |
| **CVD / VS Code course IDE** | Where the student edits, runs, tests, and develops files |

Students should not treat these as five interchangeable copies of the same thing.

### A Simple Personal Tracking System

Coaches can help the student keep one planning view with fields such as:

| Module/Week | Required Item | Where It Lives | Planned Work Block | Status | Next Action |
| --- | --- | --- | --- | --- | --- |

The specific tool—paper, calendar, spreadsheet, task app—is less important than consistently recording **where the work is and what happens next**.

If the student's GitHub repository, CVD, or local files are technically failing or out of sync, do not try to repair Git during coaching. Route the technical problem to the IT Service Desk.

## Know When to Route the Student Elsewhere

| Student Need | Primary Route |
| --- | --- |
| Time/task prioritization, organization, technical-reading strategy, study habits, learning strategies | Academic Coaching |
| Python concept, pseudocode/flowchart reasoning, debugging, testing, or programming problem solving | IT 140 faculty, LSS, and/or 24/7 Drop-In Tutoring |
| What the assignment requires, what to submit, rubric interpretation, grade, deadline, instructor feedback | IT 140 faculty |
| CVD, VS Code, Python environment, GitHub authentication/repository workflow failure, or Verify failure | IT Service Desk |
| Academic plan, course sequence, program requirements, broader persistence concern | Academic Advisor |
| Writing quality in an IT 140 written deliverable | Written Feedback |
| English-language learning support | Academic Support ELL/ESOL pathways |

A student may need several routes at the same time. Coaching does not need to wait for a separate technical or programming issue to be fully resolved if the coaching need is independent.
